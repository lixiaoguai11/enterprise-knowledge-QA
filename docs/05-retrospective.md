# 05 — 复盘：从 0 到 1 的开发决策

这份复盘记录从需求拆解到可交付程序，哪些决定帮助缩小范围、哪些风险仍未消除。它也用于指导下一位第一次接触 Agent/RAG 的开发者，避免把“能运行”误当成“答案可靠”。

## 从需求到最小可交付物

### 第一步：先写能观察的成功条件

“帮助员工找答案”太宽泛，不能直接实现。将它拆成单一证据、互相冲突、资料外、改写问题、上下文追问、工具失败和修改资料七类行为。每一类都规定用户最终看到什么状态、原文引用和缺口。

这个顺序的重要性在于：若先做 UI 或挑模型，很容易把工作量花在无法评审的功能上。先确定答案证据和失败动作，才知道需要哪些工具、字段和测试。

### 第二步：把用户入口收窄为 REPL

原仓库有服务端和前端，也夹带登录、审批等业务代码。此任务要求 CLI-only，所以收敛到一个交互循环：输入一行问题，输出一轮结果，用户可继续追问或清空上下文。减少入口有助于演示和调试，也减少需要部署的组件。

代价是没有多用户权限和 HTTP 集成。不能因为入口是 CLI 就默认真实企业文档可以给所有本机用户查看；接入生产资料前仍需设计数据访问边界。

### 第三步：先设计证据结构，再设计模型提示词

若检索只返回文本字符串，最终回答很难知道原文来自哪里。系统因此让工具结果始终带文档 ID、标题、版本日期、章节和 quote。模型生成的 citation 再用 `doc_id` 白名单和原文子串校验过滤。

这只能解决“引用确实来自这轮检索结果”，不能解决“引用足以支持整个答案”。可靠性要分层：检索是否找对材料、模型是否解释正确、引用是否真实、最后答案是否超出证据，分别评估。

### 第四步：区分模型灵活性与程序确定性

模型适合根据上下文选择检索词、决定是否读取全文、组织自然语言；程序适合严格限制轮次、校验 JSON、过滤伪造引用、捕获工具错误。高风险行为不能只写在 system prompt 里，因为 prompt 是要求，不是程序级保证。

代码目前用有限数字规则保护 D01/D02 冲突。它是针对验收点的窄保护，不是通用制度冲突引擎。下一步应先构造冲突/非冲突对照集，再决定是否引入实体属性抽取或人工审核流程。

## 关键设计点：以后遇到类似问题如何选择

| 开发问题 | 本项目当前选择 | 考虑理由 | 评审时要追问 |
|---|---|---|---|
| 先建 Agent 还是先做确定流程？ | 用模型工具调用，但把安全边界放在 Python 代码 | 需求明确要模型动态决策，同时需有限、可审查 | 哪些分支由模型决定？哪些分支由代码强制？ |
| 是否只用向量？ | 保留 BM25，向量与重排可选 | 中文制度有专有名词和 ID；词法检索容易解释，向量改善改写召回 | 是否有固定集比较召回率？首次下载失败会怎样？ |
| 冲突按日期取最新吗？ | 不取；需有明确范围/优先级文本才能判定 | 日期不等同适用规则或废止关系 | 是否明确记录版本生效、废止和范围字段？ |
| 无引用但模型觉得知道怎么办？ | `answered` 没有有效引用就降为资料不足 | 宁可要求补资料，避免常识伪装成公司制度 | citation 校验是否与答案语义支持分开？ |
| 工具报错后继续回答吗？ | 本轮立刻停止并返回 `tool_error` | 工具失败可能让证据不完整，继续生成有误导性 | 是否要区分可重试/不可重试和模型服务错误？ |
| 用真实模型写单测吗？ | 单测用替身，线上运行另留 Trace | 单测可复现且不花 API 成本；线上结果仍是另一类证据 | 评估集是否覆盖真实检索和真实调用？ |
| 会话历史要持久化吗？ | 暂时只保留进程内对话 | 最小实现避免未设计的员工数据留存 | 若持久化，如何隔离用户、删除和审计？ |
| 文档变了如何让索引同步？ | 删除本地 DB 和向量缓存后重建 | 当前没有文档增量同步与内容哈希索引 | 缓存 key 是否包含内容 hash、模型版本和分块策略？ |

## 开发中学到的工程经验

### 测试替身不能替代真实集成测试

ScriptedModel 可以复现“模型发一个 search tool call，下一轮返回 JSON”的协议路径，也能故意模拟错误答案，检查冲突保护。但它绕开真实 API、真实工具 schema 序列化和网络问题。替身越多，越要明确它模拟了哪些边界、没模拟哪些边界。

### RAG 至少有两个独立的失败点

1. **检索失败**：有正确答案但系统没把段落找出来。应看 Recall@k、目标文档排名、改写问题表现。
2. **生成失败**：工具返回了证据，但模型忽略、误读或过度概括。应看引用正确性、冲突动作、答案蕴含证据程度。

只看最终答案对错，很难定位是检索还是生成造成问题。Trace 需要保留搜索 query、命中片段/文档、原文读取和模型最终状态。

### 索引是派生数据，需要明确失效规则

SQLite、BM25 进程内结构和向量缓存是同一份资料的不同表示。替换 Markdown 不会自动改变已存在数据库；更换数据库后也不能盲信旧向量缓存。更稳健的后续设计是对源文件内容、切片策略、embedding 模型做 hash/版本标记，并基于标记增量更新或拒绝旧缓存。

### 可选依赖也会影响“第一次能不能启动”

向量和 reranker 虽然是可选能力，但当前启动时会尝试加载它们。网络源慢时，体验上就像 CLI 卡住。下一步应增加明确的快速启动选项，例如 `KB_RETRIEVAL_MODE=bm25|hybrid`，让用户可主动选择在线下载或离线 BM25；而不是只靠等异常发生后回退。

### 文档应写当前行为，不写期望行为

“模型会识别冲突”只表达了提示词要求；“代码会用规则拦截完全同句式数字差异”才是可复核的实现事实。文档里把静态代码、自动化替身结果、真实运行结果分开，能够防止评审者将设计目标误认为已达成质量。

## 当前主要未完成点

1. 提供真实 DeepSeek Key，记录至少一份真实模型运行 Trace，覆盖冲突处理并对照验收条件。
2. 在可访问模型下载源的机器上完成 CLI 启动和真实混合检索测试；记录启动时间、BM25 回退情况和首次模型下载情况。
3. 做真正的资料替换端到端验证：更新 Markdown → 重建 SQLite → 清理/重建向量 → 对同一问题运行 → 比较证据、答案、引用和状态。
4. 处理 GitHub `403` 发布问题：为当前账号授权该仓库写入，或明确目标 fork。未经权限解决前，不应报告已推送。
5. 评估是否将初次加载改为可配置 BM25-only，改进向量缓存的内容哈希失效机制。

## 交付前给自己的检查问题

- 每个答案的引用是否真来自工具，原文是否支持答案的范围和限定词？
- 若两个文档值不同，系统是否显示双方，而不是按时间、分数或模型偏好选一个？
- 换一种表述时，检索是否真的找到目标段落，而不是脚本工具直接返回预设结果？
- 修改来源文件后，数据库和缓存是否真的更新？
- 工具失败时，状态和 Trace 是否能让用户判断需要重试？
- Trace 是否说明使用真实模型还是脚本化替身？
- 文档中的“已经”是否能由代码或实际运行记录支撑？
